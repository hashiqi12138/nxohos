# P2.1 Game Data Distribution — Implementation Record

Status: **implemented and device-verified** (2026-11-15). Design: `DESIGN-P2.1-GameDataDistribution.md`.
Code: nested `nxnative` `8eeafa3f`, outer `fb53476`.

## 1. What changed

Game data (14.75 GB, 41,084 files) no longer rides in five feature-module HAPs. It is one `.nxpk` file
that the app imports into its own sandbox, once.

| Piece | File | Role |
|---|---|---|
| Container builder | `dm/tools/pack_game.py` | porter pack dir → `.nxpk` (80-byte header + ustar stream); `--check` validates |
| Manifest generator | `dm/tools/gen_pack_manifest.py` | `dm.files.tsv` (stamp over rel/size/mtime), called by pack_game when absent |
| Dev server | `dm/tools/pack_server.py` | serves `/ping`, `/stamp` (80 B), `/pack.nxpk` (Range/206), `/dm.files.tsv` |
| App importer | `dm/ohos/hap/entry/.../PackImport.ets` | header parse, streaming ustar unpack, stamp read/write, removeTree |
| App wiring | `dm/ohos/hap/entry/.../Index.ets` | DocumentViewPicker, launcher panel, progress, loopback download + resume, watchdog |
| Permission | `dm/ohos/hap/entry/src/main/module.json5` | `ohos.permission.INTERNET` (loopback channel) |
| Dev loop | `dm/ohos/devpush.py` | `--data-dir` serves the pack, `--import-wait` watches the import |
| Fixup helper | `dm/tools/fix_utf8_dashes.py` | repairs UTF-8 truncated by a PowerShell round-trip (see §5.9) |

## 2. The container format

```
offset  size  field
0       8     "NXPK" + version(1) + 3 reserved
8       16    title ID, ASCII, NUL-padded
24      48    pack stamp, ASCII sha1-hex, NUL-padded
72      8     tar size, little-endian u64
80      ...   ustar stream
```

The tar is produced by Python's `tarfile` (USTAR format) — the format is not invented, only framed. The app
validates magic, title and size before unpacking 14.75 GB.

Verified: `pack_game.py --check` on the BOTW pack reports
`version 1, title 01007EF00011E000, stamp dccb848e7ac5649acd9819fabe713003d6fbf952`,
`tar 15839232000 bytes, file 15839232080 bytes -> consistent`, `members: 41981`.

## 3. Why the app must import it

Two SELinux walls, both measured on the device:

| Direction | Attempt | Result |
|---|---|---|
| shell → app sandbox | `hdc file send ... /data/app/el2/100/base/<bundle>/files/...` | `permission denied` (`debug_hap_data_file`) |
| app → shell tmp | `fs.listFileSync('/data/local/tmp/...')` in ArkTS | throws (`data_local_tmp`) |
| shell → `/storage/media` | `touch /storage/media/100/local/files/Docs/x` | `permission denied` |
| `run-as` | `hdc shell run-as <bundle> id` | `inaccessible or not found` |

So the pack reaches the sandbox through exactly one door: the app reads it. Two sources feed that door:

1. **User path** — `DocumentViewPicker` (`.nxpk` filter) → `PackImport.importPack(uri, root, ...)`.
2. **Dev path** — `hdc rport tcp:28899 tcp:28899` forwards the device's loopback to `pack_server.py`;
   the app streams `/pack.nxpk` into `cache/pack.nxpk.part` and imports the same way.

Both share every line of the importer. `hdc fport` is the wrong direction here: it listens on the device,
which needs that port free; `rport` listens on the PC and the device dials out.

## 4. The stamp contract

`dm.files.tsv` starts with `# DM_DATA <sha1>` over `(rel, size, mtime_ns)`. `pack_game.py` copies that sha1
into the container header; the app writes it to `files/dm/.stamp` after a successful import.

Three checks, cheapest first:

1. `GET /stamp` → 80 bytes. Equal to `.stamp` → done. **This is what makes a debug round cost 80 bytes.**
2. A complete `cache/pack.nxpk` → unpack it, no download.
3. `cache/pack.nxpk.part` → `Range: bytes=<have>-`, append, resume.

Verified sequence on the device:

```
staging: server pack stamp dccb848e7ac5, sandbox empty
staging: download target .../pack.nxpk.part (fd 55, from 0)
staging: requestInStream begins
...
staging: requestInStream -> 206, total 15839232080 bytes
staging: have 15839232080 of 15839232080 bytes (100%)
staging: using the cached container (15105 MB, stamp dccb848e7ac5)
staging: unpacked 41106 files from the cached pack
starting the game
napi: game thread started (root=/data/storage/el2/base/haps/entry/files/dm)
[dm] >>> nnosInitialize
```

Second start:

```
staging: server pack stamp dccb848e7ac5, sandbox dccb848e7ac5
staging: stamp match, skipping the download entirely
starting the game
[dm] >>> nnosInitialize
```

12.5 s from `aa start` to the game thread, with no transfer, no unpack, no copy.

## 5. Defects found while bringing the path up

Nine, in the order they bit. Each was found on the device, not in review.

### 5.1 ARRAY_BUFFER buffered the whole pack

`http.request` with `expectDataType: ARRAY_BUFFER` collects the entire body in memory. It died at 52 MB:
`code 2300023 Failed to write the received data to the disk`.
**Fix:** `requestInStream` + `dataReceive`, each chunk written straight to the file descriptor.

### 5.2 `fs.openSync(...).fd` failed silently

Taking `.fd` off the returned `File` and dropping the object left the descriptor to be collected; the file
was never created and the write errors vanished into a catch.
**Fix:** keep the `fs.File` object for the lifetime of the download, close it in `finally`.

### 5.3 readTimeout is the whole request's budget

`readTimeout: 3600000` (one hour) is not a per-read timeout. 14.75 GB at the measured 4.09 MB/s needs ~62
minutes, so the request threw `2300028 Operation timeout` **after receiving every byte** (`dlSz` equalled
`Content-Length`), and the completed file was discarded.
**Fix:** `readTimeout: 21600000` (six hours), and a timeout no longer discards what arrived — the tar reader
judges the file.

### 5.4 The download ran before the stamp check

Every round pulled 14.75 GB and then discovered the data was already there.
**Fix:** the `/stamp` endpoint. A round whose data is current costs one 80-byte request.

### 5.5 dataReceiveProgress never fires under requestInStream

The progress panel sat at 0% through 5.5 GB. `dataReceiveProgress` is documented but does not fire for this
call on this device.
**Fix:** accumulate `wrote` in `dataReceive` and compute the percentage from `80 + tarSize`, read back from
the header once 80 bytes are in.

### 5.6 A TCP half-open link stalled for 17 minutes

The device's socket stayed `Established` while the WiFi link was gone; no data arrived and no error was
raised. With a six-hour `readTimeout` it would have waited six hours.
**Fix:** a 10-second-interval watchdog that destroys the request after 60 s without a byte. That surfaces as
an error, `.part` keeps what arrived, the next start resumes.

### 5.7 THREAD_BLOCK_6S — the system killed the process

The big one. The unpacker ran as one long synchronous loop on the ArkTS thread. HarmonyOS kills a foreground
app whose thread blocks for six seconds, with **no crash signal in hilog** — the process simply vanished:

```
foundation/AppMS: [AMSI6516] ... send event [FRAMEWORK,PROCESS_KILL],
pid=9433, processName=dev.eden_emu.ohos, msg=THREAD_BLOCK_6S, reason=THREAD_BLOCK_6S, FOREGROUND=1
```

It looked like a random crash at three different points. The yield granularity had to be tightened three
times before the whole pack went through:

| Yield policy | Outcome |
|---|---|
| none | died at 180 MB |
| every 200 files, `setTimeout(0)` | died at 5 GB |
| every 20 files / 8 MB, `setTimeout(0)` | died at 6 GB |
| **every 5 files / 1 MB, `setTimeout(1)`** | **41,106 files, no kill** |

`setTimeout(0)` in ArkTS still drains microtasks in the same turn, so it is not enough; 1 ms actually yields.
The byte-based check matters too: a single 500 MB asset would otherwise hold the thread for seconds.

### 5.8 `lseek` did not hold — the reader started at offset 0

`fs.lseek(fd, 80, SEEK_SET)` once, then `readSync(fd, buf, {offset: 0, length: 512})` for 41k iterations. The
reader ended up parsing the container header as a tar header and made a **0-byte file named `NXPK`**.
`ReadOptions.offset` is the file position, not a buffer offset, and passing it on every call is
self-correcting.
**Fix:** track `pos` in the loop and pass `{offset: pos, length: n}`; drop `lseek` entirely.

### 5.9 A short file was renamed and read as complete

A 1.1 GB partial was renamed to `pack.nxpk` and handed to the reader, which imported a handful of files and
left a broken sandbox.
**Fix:** verify `wrote == 80 + tarSize` from the container's own header; a short file stays `.part` and the
next start resumes it.

### 5.10 Side note: PowerShell truncated the UTF-8 source

`-replace` + `Set-Content -NoNewline` on a UTF-8 file routes through the console's cp936 page, turning `—`
(E2 80 94) and `→` (E2 86 92) into `E2 80 3F` / `E2 86 3F`. ArkTS then reported
`Unterminated string constant`. `dm/tools/fix_utf8_dashes.py` repairs such a file; the dpad labels were also
normalized to ASCII (`UP`/`DN`/`LT`/`RT`) so a round-trip cannot break them again.

## 6. Resume

The download lands in `cache/pack.nxpk.part` and is **not** removed on failure. A restart measures it and
sends `Range: bytes=<have>-`; the server answers `206` with `Content-Range`. Verified across three kinds of
interruption:

| Interruption | Evidence |
|---|---|
| `aa force-stop` mid-pull | `part 1,171,634,219` → `1,267,118,714` on disk → `resuming at 1267118714` |
| `bm install -r` (app replaced) | `part 6.58 GB` survived → `resuming at 7068407984` |
| link drop (half-open socket) | watchdog fires at 60 s, next start resumes |

The `.part` lives in `haps/entry/cache/`, which an app update does not clear.

## 7. Cost model

| Round | Before P2.1 | After |
|---|---|---|
| host-only change | 20-70 min (5 HAPs re-packed, 598 MB entry, 6-module install, 41k staging) | **~1.5 min** (40 s lib, 13 s pack 4.6 MB, 1 s send, 20 s install, 80-byte stamp check) |
| data changed | same | one import (~2 min once the pack is on the device) |
| first ever install (user) | n/a | USB copy of one `.nxpk` + in-app import |

Measured transfer rates that set these numbers: hdc TCP PC→device 7.3 MB/s, device→PC 1.8 MB/s (hdc's own
protocol, not WiFi); loopback `requestInStream` 4.09 MB/s average, 10.4 MB/s on a good stretch. The user path
never uses either: the picker reads the phone's own storage.

## 8. User path (no programming)

1. Get the `.nxpk` onto the phone: USB copy, Huawei Share, cloud drive — one file, 14.75 GB.
2. Open the app. With no data the launcher appears: "No game data yet" + **Add game (.nxpk)**.
3. Pick the file. The panel shows `downloading N / M MB`, then `unpacking`, then the game starts.
4. Later launches skip all of it (stamp match).
