# P2.3 存档导出/导入：详细设计

> 阶段：**设计评审**。定稿后实现。
> 依赖：S1 令牌、S4 详情抽屉、P1.6 设置页

---

## 1. 事实核查（先查证，不假设）

| 事实 | 证据 |
|---|---|
| 存档目录 `files/save` | `front_ohos.c:88` `setenv("DM_SAVE", save)` |
| 存档是**事务性**的 | 日志：`transactional save: work directory, swapped in atomically on Commit` |
| 提交实测 5.5 ms | 日志：`save commit #1: ... (clone + swap 5504 us)` |
| 存档与游戏数据**分开** | `files/games/<title>/` vs `files/save` |
| shell 读不了存档 | `ls files/save/` → `Permission denied`（SELinux 双墙） |

**关键约束**：存档**只能由应用自己读写**。导出/导入必须走应用内路径（picker），不能用 hdc。

---

## 2. 存档的目录结构（需要实测确认）

`DM_SAVE` 指向一个目录，native 层在其上做 mount。实际结构需要查 `hle_fs.c` 的 mount 逻辑：

- 如果存档按 title 分目录（`save/<title-id>/...`），多游戏天然隔离
- 如果所有游戏共用一个 `save/`，多游戏会**互相覆盖**——这是必须先确认的

**这是设计前必须查清的第一件事。**

---

## 3. 用户需求

| 场景 | 用户想做什么 |
|---|---|
| **备份** | 玩到关键进度，导出一份存档到安全的地方 |
| **迁移** | 换设备/重装应用，把存档带过去 |
| **回滚** | 玩崩了（存档损坏、误操作），恢复之前的备份 |
| **分享** | 把存档发给朋友（少见但存在） |

**共同点**：都需要一个**文件**（可复制、可存放、可传输）。

## 4. 界面设计

### 4.1 入口

**两处**：
1. **游戏详情抽屉**（S4 已有）：加「导出存档」「导入存档」两个按钮
2. **设置 → 数据**：加「存档管理」（列出所有游戏的存档大小，批量导出）

**为什么两处**：详情抽屉是"针对这个游戏"的自然位置；设置里是"全局管理"（换设备时一次性导出全部）。

### 4.2 导出流程

```
详情抽屉 → 点「导出存档」
  ↓
系统保存对话框（DocumentViewPicker.save）
  默认文件名：<游戏名>-<日期>.nxsave
  ↓
打包存档目录 → 写入用户选的位置
  ↓
Toast：「已导出 2.3 MB 到 下载/xxx.nxsave」
```

**进度**：存档通常几 MB（远小于 14.7 GB 的游戏数据），几秒内完成。**不需要进度条**，但超过 2 秒要给反馈（转圈）。

### 4.3 导入流程

```
详情抽屉 → 点「导入存档」
  ↓
系统文件选择器（DocumentViewPicker.select，.nxsave）
  ↓
读包校验（magic + title ID）
  ├─ title 不匹配 → 错误「这不是这个游戏的存档」
  └─ 匹配 ↓
二次确认：
  「导入存档？
   将覆盖当前的游戏进度。
   当前进度会先备份到 .backup，可以撤销。
   [取消] [导入]」
  ↓
备份当前存档 → 解包覆盖 → Toast「已导入，重新进入游戏生效」
```

**关键设计**：**导入前自动备份当前存档**。玩家点错也能救回来。这是存档功能最重要的安全网。

### 4.4 存档管理（设置页）

```
存档
  塞尔达传说      2.3 MB    [导出]
  马力欧 奥德赛    1.1 MB    [导出]
  ─────────────────────────
  [导出全部]      3.4 MB
```

## 5. 文件格式：`.nxsave`

**为什么不直接导出目录**：`DocumentViewPicker` 只能保存**单个文件**，不能保存目录。所以必须打包。

```
┌─────────────────────────────────────────┐
│ magic "NXSAVE\0\0"  (8 B)              │
│ version             (1 B)  = 1          │
│ reserved            (7 B)               │
│ title ID            (16 B, ASCII)       │
│ created at          (8 B, unix seconds) │
│ tar size            (8 B, u64 LE)       │
├─────────────────────────────────────────┤
│ ustar tar stream (存档目录的全部内容)     │
└─────────────────────────────────────────┘
```

**48 字节头 + tar 流**——和 `.nxpk` 同一套思路（P2.1 已验证可靠），但更小。

**为什么用 tar 而不是 zip**：OHOS 没有内置 zip 库；tar 是纯格式，`@ohos.zlib` 不需要。P2.1 的 `PackImport.ets` 已有 ustar 解包代码，**可以复用**。

## 6. 实现清单

| # | 文件 | 内容 |
|---|---|---|
| 1 | `pages/SaveData.ets` | `packSave()` / `unpackSave()` / `saveDir()` / `backupSave()` |
| 2 | `components/GameDetailSheet.ets` | 加「导出存档」「导入存档」按钮 |
| 3 | `pages/LibraryPage.ets` | 接入 picker（save/select）+ 二次确认 |
| 4 | `pages/SettingsPage.ets` | 存档管理组（列出各游戏存档大小 + 导出全部） |

### 验收标准

1. 详情抽屉有「导出存档」，点击弹出系统保存对话框
2. 导出生成 `.nxsave` 文件，大小与实际存档一致
3. 导入校验 title ID，不匹配时报错不崩
4. 导入前自动备份当前存档到 `.backup`
5. 导入后能撤销（备份还在）
6. 设置页列出各游戏存档大小
7. 多游戏存档**互不干扰**（关键，需先确认目录结构）

## 7. 本步不做

| 不做 | 理由 |
|---|---|
| 云同步 | 没有后端 |
| 自动备份（定时） | 需要后台任务，OHOS 限制多 |
| 存档编辑器（改数值） | 需要理解每个游戏的存档格式，不可能通用 |
| 跨设备直传 | 需要网络发现，P2.5 之后再说 |

## 8. 必须先查清的三件事

在写代码前必须确认，否则设计可能整体作废：

1. **存档目录是否按 title 分？**
   - 如果共用 `save/`，多游戏会互相覆盖，需要先改成 `save/<title>/`
   - 这是 P2.3 的**前置条件**，也可能是 P2.1 遗留的缺陷

2. **`DocumentViewPicker.save()` 在 OHOS 上的签名和权限**
   - 需要确认能否指定文件名和扩展名

3. **存档的实际大小和文件数**
   - 决定是否需要进度条
