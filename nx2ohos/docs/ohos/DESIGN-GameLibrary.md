# 游戏库：产品设计文档

> 状态：**设计评审中**，未开始实现。
> 上一版（`aba13c8`）是功能验证用的调试面板，不是产品。本文件重新从用户与场景出发。

---

## 1. 这个产品是什么

**一句话**：一个让玩家在鸿蒙设备上管理、启动 Switch 游戏的启动器。

**它不是**：文件管理器、设置页、调试工具。

**它服务的时刻**：玩家坐下来想玩游戏的那一刻。开机 → 找到想玩的 → 进入 → 玩。全程应该 15 秒内完成，不需要思考。

---

## 2. 用户与场景

### 2.1 三类用户

| 用户 | 特征 | 关键需求 |
|---|---|---|
| **玩家**（主要） | 有 1-5 个游戏，不关心技术细节 | 快速启动；知道哪些能玩；不误删存档 |
| **进阶玩家** | 自己 porter 打包，会换游戏 | 导入新包；看到版本/来源；替换旧数据 |
| **我们（开发）** | 每天几十次调试 | 快速重装；看日志；不干扰玩家路径 |

**设计含义**：玩家路径必须是**默认路径**，开发能力藏在后面而不是摆在首页。

### 2.2 使用场景

| 场景 | 环境 | 约束 |
|---|---|---|
| 客厅横屏玩 | 手柄/触屏，距离 1-2 米 | 大字号、大焦点、暗环境 |
| 通勤竖屏 | 单手握持 | 拇指可达区、竖屏布局 |
| 首次使用 | 无数据 | 必须明确告诉用户"下一步做什么" |
| 导入 14.7 GB | 等待 10-60 分钟 | 可离开、可中断、回来能继续 |

**设计含义**：横屏是主场景，竖屏不能崩；导入必须可后台化。

## 3. 需求清单（按优先级）

### P0 — 没有它产品不成立

| # | 需求 | 验收标准 |

| R9 | 游戏元数据 | 显示版本、大小、导入时间、来源 |

## 4. 信息架构

```
启动
 │
 ├─ 有游戏 ──→ 游戏库（默认）
 │              ├─ 游戏卡片 → 启动
 │              ├─ 长按/菜单键 → 详情
 │              │                 ├─ 版本、大小、来源
 │              │                 ├─ 删除（二次确认）
 │              │                 └─ 校验完整性
 │              └─ 添加游戏 → 文件选择器 → 导入进度 → 完成回库
 │
 └─ 无游戏 ──→ 空状态
                └─ 导入游戏 → 同上
```

**关键决策**：有游戏时**默认进游戏库**，不是直接启动上次的游戏。理由：玩家可能想换游戏，直接启动剥夺了选择权；且启动器是产品的主界面，不该被跳过。

> 注：这一条与当前实现相反（当前有数据直接进游戏）。改为库优先需要用户确认。

## 5. 界面设计

### 5.1 视觉语言

**参考坐标**：Switch 主界面（简洁、大图标、横向排列）、Steam Deck 库（列表+详情）、Apple TV（焦点放大）。

**风格**：`Modern Dark (Cinema Mobile)`

| 令牌 | 值 | 用途 |
|---|---|---|
| `--bg` | `#0F172A` | 背景（不用纯黑，避免 OLED 拖影） |
| `--surface` | `#192134` | 卡片 |
| `--surface-raised` | `#201A32` | 悬停/焦点卡片 |
| `--text` | `#FFFFFF` | 主文字 |
| `--text-dim` | `#94A3B8` | 次要文字（对比度 4.6:1） |
| `--accent` | `#EC4899` | 焦点环、主按钮 |
| `--danger` | `#DC2626` | 删除 |
| `--border` | `rgba(255,255,255,0.08)` | 分隔线 |

**字体**：标题 Orbitron（科技感，游戏库合适）；正文用系统字体（中文覆盖、可读性优先，不用 JetBrains Mono 做正文——中文等宽字体丑且慢）。

**图标**：统一线性图标（Lucide 风格），**不用 emoji**。

### 5.5 导入进度

**这是用户会盯着看 10-60 分钟的界面，必须做好。**

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  正在导入 塞尔达传说 王国之泪                              │
│                                                          │
│  ┌────────────────────────────────────────────────┐     │
│  │██████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░│     │  ← 42%
│  └────────────────────────────────────────────────┘     │
│                                                          │
│  6.2 GB / 14.7 GB          约 18 分钟                    │
│                                                          │
│  正在写入 RomFS/Model/Character/...                      │
│                                                          │
│              ┌──────────────┐                            │
│              │   后台继续   │                            │
│              └──────────────┘                            │
│                                                          │
│  可以离开此页面，导入会继续。中断后重新打开会从断点继续。    │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**要点**：
- **剩余时间**而不只是百分比（百分比 42% 对 60 分钟意味着什么？）
- 当前文件路径给"还在动"的确认感，但用省略号截断
- "后台继续"是主操作，不是"取消"——导入是长任务，取消是次要的（放在角落或菜单里）
- 明确告知**断点续传**，降低焦虑
- 进度条不用 spinner（长时间任务需要确定性进度）

**取消导入**：放在右上角 `×`，二次确认："已下载 6.2 GB，取消后需要重新开始。确定？"

### 6.1 触摸

| 元素 | 最小尺寸 | 反馈 |
|---|---|---|
| 游戏卡片 | 320×180 dp | 按下缩放 0.97，150ms |
| 按钮 | 48 dp 高 | 按下背景变亮，100ms |
| 图标按钮 | 48×48 dp（视觉 24） | 按下缩放 0.9 |

### 6.2 手柄/键盘

| 键 | 行为 |
|---|---|
| 方向键 | 焦点在卡片间移动，边界不循环 |
| A / Enter | 启动选中的游戏 |
| 菜单 / M | 打开详情 |
| B / Esc | 关闭当前面板/返回 |

**焦点必须可见**：粉色 2dp 描边 + 卡片放大 1.08 + 微光。

### 6.3 状态与反馈

| 状态 | 表现 |
|---|---|
| 加载库（<200ms）| 不显示 loading（避免闪烁）|
| 加载库（>200ms）| 骨架屏（卡片轮廓）|

| 启动失败 | 卡片变红边 + 底部 toast 说明原因 |
| 数据不完整 | 卡片灰显 + "数据不完整，请重新导入" |
| 导入中 | 顶栏显示进度条，可继续浏览其他游戏 |

## 7. 边界情况

| 情况 | 处理 |
|---|---|
| 零游戏 | 空状态页 |
| 一个游戏 | 网格居中，不拉满 |
| 游戏数据损坏 | 卡片标记"不完整"，Play 禁用，提示重新导入 |
| 导入时磁盘满 | 立即停止，明确提示"存储空间不足，需要 X GB" |
| 导入时应用被杀 | 下次启动检测 `.part`，提示"发现未完成的导入，继续？" |
| 同名游戏重复导入 | 提示"已存在，覆盖？"（按 title ID 判断）|
| 导入错误的文件 | 提示"这不是游戏包"，不崩溃 |
| 游戏运行中打开库 | 面板叠加，提示"重启应用以切换游戏" |

## 8. 技术约束（影响设计的部分）

| 约束 | 设计影响 |
|---|---|
| guest 独占 native 线程，无法停止 | 游戏内无法真正切游戏；库里 Play 需重启生效 |
| shell 无法写沙盒 | 导入必须走应用内（picker 或 loopback）|
| 解包必须细粒度 yield | 导入期间 UI 必须保持响应（进度条能动）|
| 41k 文件 stat 慢 | 体积计算需预算上限；或用 `.stamp` 旁的元数据缓存 |

## 10. 已确认的三个决策

### 决策 1：默认进库 ✅

启动应用 → **游戏库**（有游戏时）。玩家自己点卡片启动。

**理由**：启动器是产品主界面。直接启动上次的游戏剥夺了选择权，且让"库"这个核心界面永远看不到。

**代价**：从点击图标到进游戏多一次点击。用「记住上次游戏 + 库首项高亮」缓解。

### 决策 2：真封面 ✅（但需要 porter 配合）

**查证结果（2026-11-16）**：

| 事实 | 结论 |
|---|---|
| BOTW 的 RomFS 里没有 `icon/` 目录 | Switch 图标不在 RomFS，在 NCA 的 **control 分区** |
| porter 数据包（`ZeldaBreathOfTheWild-data-ohos`）没有图标文件 | porter 当前不提取图标 |
| `nx2a-data.json` 有名称/版本/文件数/字节数 | 但**没有图标字段** |
| 上游 iOS/Android 前端 | 不显示游戏图标（纯文字列表）|

**所以"真封面"需要 porter 先导出图标。** 两条路径：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. porter 导出（推荐）** | porter 从 NCA control 提取 `icon_*.jpg`，写进数据包 | 改 porter（Python，我们自己的工具，非上游 C 代码）|
| **B. 应用内提取** | 应用从 RomFS 找图标 | **不可行**：图标根本不在 RomFS |

**采用方案 A**，分两阶段：

**阶段 1（现在做，不阻塞 UI）**：
- `nx2a-data.json` 增加 `"icon"` 字段（相对路径，如 `"icon.jpg"`）
- 应用读这个字段；文件存在则显示，不存在走占位
- **不阻塞**：现在没有图标，先显示占位；porter 更新后自动生效

**阶段 2（porter 侧，独立任务）**：
- porter 从 NCA control 提取图标，存为 `<pack>/icon.jpg`
- 写进 `nx2a-data.json` 的 `"icon"` 字段
- 打 `.nxpk` 时一起打进去

**占位封面设计**（必须有，不是可选项）：

```
┌──────────────────┐
│                  │
│                  │
│        塞        │   ← 游戏名首字，56sp，#475569
│                  │
│                  │
└──────────────────┘
  塞尔达传说 王国之泪   ← 卡片下方文字
  14.7 GB  ·  可运行
```

- 背景 `#1E293B`（比卡片底色深一档，有层次）
- 首字居中，56sp，`#475569`（对比度 3.2:1，装饰性文字不要求 4.5:1）
- **不同游戏用不同底色**（从 title ID 哈希到 6 个预设色之一），避免一片灰

**为什么这个占位是对的**：玩家能一眼区分不同游戏（首字+颜色），且明显是"占位"而非"加载失败"。

---

### 决策 3：游戏内返回库 = 终止进程并重启 ✅

**已确认不需要动上游。** 技术路径：

```
用户在游戏里长按左上角
  ↓
ArkTS: 弹出确认"退出游戏并返回库？未保存的进度会丢失。"
  ↓ 确认
ArkTS: ctx.terminateSelf()       ← UIAbilityContext，Promise 形式
  ↓
系统结束 ability，进程退出（内核回收 GPU 上下文、线程、fd）
  ↓
玩家重新点图标 → 冷启动 → 库
```

**为什么用进程退出而不是停线程**：

| 方案 | 问题 |
|---|---|
| `pthread_cancel(guest)` | guest 线程 `pthread_detach` 过，无法 join；强杀会破坏 GPU 命令缓冲、文件句柄、Metal/Vulkan 对象 |
| 设置退出标志让 `nnMain` 返回 | `nnMain` 是**游戏自己的代码**，没有退出钩子；注入需要改 guest 二进制 |
| **`terminateSelf()`** | **系统级安全终止**：内核回收所有资源，无泄漏风险。文档明确支持"询问用户确认后关闭"的场景 |

**API 细节**（查证 `@ohos.app.ability.UIAbility`）：
- `terminateSelf(): Promise<void>` — 用这个（回调形式在部分设备不执行）
- 在 `onDestroy` 里清理；文档警告：onDestroy 完成后应用可能退出，未完成的异步操作会被中断

**代价**：冷启动约 15-20 秒。**产品上可接受**——玩家主动退出游戏时等 20 秒回库是合理预期。

**实现要点**：
- 只在**游戏运行时**显示这个入口
- 二次确认，文案说明未存档进度会丢失
- 退出后库**不自动启动**任何游戏（决策 1）

## 12. 封面提取的技术细节

Switch 图标路径（标准）：
```
RomFS/icon/NintendoSwitch/icon_*.jpg     ← 256x256 或 1024x1024
```

提取流程（导入完成后）：
1. 扫描 `RomFS/icon/NintendoSwitch/`，取第一个 `icon_*.jpg`
2. 复制到 `<game-root>/.cover.jpg`
3. 库列表读 `.cover.jpg`；不存在则生成占位

**占位封面**：`#1E293B` 背景 + 游戏名首字（大号、居中、`#475569`）。不空白，不像错误。

**尺寸**：卡片 16:9，但 Switch 图标是 1:1。处理：
- 卡片内图标区居中显示 1:1 图标（不拉伸）
- 卡片其余部分是渐变色背景（从图标主色提取，或用固定深色）

或者更简单：卡片做成 **1:1 正方形**（像 Switch 主界面那样），图标直接铺满。横屏 1260 高能放 4 个 260×260 卡片。**这个更接近 Switch 的真实体验**。
