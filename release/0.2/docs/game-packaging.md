# 游戏分发制作方式

NXOHOS 把「运行环境」和「游戏数据」彻底分开：

| 内容 | 载体 | 何时变化 |
|---|---|---|
| 运行环境（`libdmhost.so` + ArkTS 界面） | HAP | 宿主代码升级时（约 3 MB） |
| 一个游戏的全部内容 | `.nxpk` 数据包 | 该游戏数据/着色器变化时（数 GB 到十几 GB） |

因此新增游戏、更新游戏都不需要重新发版应用。

## 1. 准备数据包目录（porter 产物）

移植工具（porter）对一个游戏生成如下目录：

```
<标题ID>/
  RomFS/            解包后的游戏资源
  mods/             重写后的可执行模块（main.patched.bin 等）
  shaders.dmsv      翻译好的着色器包
  env.txt           运行时环境变量（可选）
  nx2a-data.json    移植标记（必需）
```

要求：`mods/main.patched.bin` 与 `RomFS/` 必须存在，否则卡片会显示"不完整"。

## 2. 打包成 `.nxpk`

```bash
python dm/tools/pack_game.py --pack <上一步的目录> --title 01007EF00011E000 --out 01007EF00011E000.nxpk
```

打包时自动完成：

1. **写入 `profile.tsv`**（0.2 新增）：由 `dm/games/<标题ID>/game.tsv` 生成，内含该游戏的模块列表、内存布局、帧率目标等常量。宿主编译期不再需要这个游戏。
2. **纳入戳记（stamp）**：`profile.tsv` 与所有文件一起参与 `dm.files.tsv` 的哈希。数据包内容变化 → stamp 变化 → 应用会要求重新导入。
3. **GNU tar 格式**（0.2 新增）：支持长度超过 100 字节的文件名（ustar 无法编码）。
4. **容器头**：80 字节 `NXPK` 头（魔数、版本、标题 ID、stamp、tar 大小），应用按头判断是否已安装同版本。

## 3. 提供下载

把生成的 `.nxpk` 放在任意 HTTP 静态目录下：

```
http://<主机>:<端口>/01007EF00011E000.nxpk
http://<主机>:<端口>/01002B30028F6000.nxpk
```

应用通过库页的「可下载」列表读取该目录的包清单（示例环境：`192.168.2.2:28899`）。文件名建议为 `<标题ID>.nxpk`，便于识别。

## 4. 版本与更新

- 同一标题 ID、stamp 相同的包：应用显示"已安装"，下载会被跳过。
- stamp 不同（数据或 `profile.tsv` 有变化）：下载按钮恢复可用，安装时按数据包内实际包含的顶层目录替换——**增量包不会清空未包含的目录**（例如只更新 `shaders.dmsv` 不会删除 `RomFS/`）。
- 想强制重装：在库页删除该游戏（只删数据，存档另行保留），再下载。

## 5. 多游戏与单一宿主

一个 HAP 可以运行任意多个已安装的游戏。宿主启动时读取 `<游戏目录>/profile.tsv` 填充该游戏的常量表；若旧包没有 `profile.tsv`，回退到宿主内置的默认配置（行为等同 0.1 的内置宿主）。设计细节见 [DESIGN-P4.1](../../nx2ohos/docs/ohos/DESIGN-P4.1-SingleHostRuntimeProfile.md)。
