### TC0-2-2 从 FAIL 到 PASS 的根因（重要架构结论）

上一轮 `vkCreateSwapchainKHR` 返回 -1000000000（VK_ERROR_SURFACE_LOST_KHR），
原因是**探针把 vk 检查放在 `fork()` 出来的隔离子进程里执行**。Vulkan 的
`VkSurfaceKHR`/swapchain 与进程级的图形客户端连接（display/window manager 句柄）
强绑定，fork 出的子进程拿到的窗口是"父进程的连接"，驱动侧判定 surface 已失效。
同一份代码在父进程内直接跑即成功。

修正（本次提交）：

1. 新增 `run_inline()`，`vk_surface` 改在父进程内执行（其余检查仍 fork 隔离）；
2. 建 surface 前对 `OHNativeWindow` 执行 `SET_BUFFER_GEOMETRY`（对齐 `caps.currentExtent`）；
3. `compositeAlpha` 改为从 `caps.supportedCompositeAlpha` 选取，不再硬编码 OPAQUE；
4. `imageUsage` 与 `caps.supportedUsageFlags` 求交，保证 TRANSFER_DST 存在；
5. 建 swapchain 失败重试 3 次（每次 200ms），失败 note 带 rc/ext/alpha/usage 便于定位。

> 架构含义：M1 之后凡是"要用图形栈"的模块都不能放在 fork 隔离进程里；
> 崩溃隔离只能用于纯 CPU 检查（mem/regs/tls/futex/wx）。这条要写进 M1.1 设计约束。

对应验证手段：云调试「控制参数 → Shell脚本」可直接 `aa start` 拉活，配合 HiLog 面板
实时看 `probe:` 行（本轮已打通），无需人工点图标。

| 占位（本仓 vk_ohos_shim.h） | SDK 真名 | 头文件 |

## 结论

- 结论：**PASS**（TC0-2-1 / TC0-2-2 / TC0-2-3 全过）
- 备注：swapchain 之前的 SURFACE_LOST 是 fork 隔离导致的假阴性，改进程内执行后
  300 帧、2.337ms/帧正常上屏；该结论同时修正了 G0.3 的 ASTC 判定（见 G0.3）。
